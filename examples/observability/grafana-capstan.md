# Grafana и телеметрия Capstan — простая инструкция

## 1. Что это и где работает

Это **локальный диагностический стенд на твоём Mac**, не облачный сервис. Регистрация на grafana.com не нужна.

```text
Capstan — измеряет операции и создаёт события
   ↓ OTLP по HTTP, http://127.0.0.1:4318
OpenTelemetry Collector — принимает и распределяет данные
   ├─ Tempo — хранит трейсы (деревья операций с длительностью)
   ├─ Loki — хранит логи (события с контекстом)
   └─ Prometheus — компонент для метрик в комплекте LGTM
                 ↓
Grafana — показывает данные в браузере, http://127.0.0.1:3000
```

Эти сервисы упакованы в **один Docker-контейнер** `grafana/otel-lgtm:0.29.0`. Docker на этом Mac работает через OrbStack. Grafana — интерфейс, а не само хранилище трейсов или логов.

Проверено по работающему Docker:

| Что | Где |
| --- | --- |
| Проект Docker Compose | `/Users/alxd/narnia/telemetry-dash` |
| Файл развёртывания | `/Users/alxd/narnia/telemetry-dash/compose.yaml` |
| Контейнер | `telemetry-dash-lgtm-1` |
| Веб-интерфейс | http://127.0.0.1:3000 |
| Приёмник OTLP/HTTP | http://127.0.0.1:4318 |
| Данные | Docker-том `telemetry-dash_lgtm-data`, внутри контейнера `/data` |
| Политика перезапуска | `unless-stopped` |
| Автоматически подключаемый дашборд | `telemetry-dash/capstan.json` |
| Настройка подключения дашборда | `telemetry-dash/dashboards.yaml` |

Порты опубликованы только на `127.0.0.1`: с другой машины эти ссылки не откроются. Пути Compose и подключений получены из метаданных контейнера; содержимое внешнего Compose-файла здесь не проверялось. Секреты и учётные данные в этой инструкции не хранятся.

## 2. Как включить и выключить

Обычный запуск:

1. Открой **OrbStack** и дождись запуска Docker.
2. Открой [Grafana](http://127.0.0.1:3000).
3. Если страница недоступна, в терминале проверь и запусти существующий контейнер:

```sh
docker ps -a --filter name=telemetry-dash-lgtm-1
docker start telemetry-dash-lgtm-1
```

Развёртывание из уже существующего проекта Compose:

```sh
cd /Users/alxd/narnia/telemetry-dash
docker compose up -d
docker compose ps
```

Эта команда использует текущий `compose.yaml`; новый стенд рядом создавать не нужно. На чистой машине сначала нужны файлы этого проекта и Docker. Эта инструкция не является резервной копией Compose или данных.

Остановить без удаления данных:

```sh
docker stop telemetry-dash-lgtm-1
```

**Не запускай `docker compose down -v` и не удаляй том:** это может уничтожить сохранённую телеметрию и настройки. Автоперезапуск не заменяет резервное копирование; срок хранения данных здесь не проверен. Образ otel-lgtm предназначен для разработки и тестирования, не для готового производственного развёртывания.

## 3. Какие дашборды есть

[Все дашборды](http://127.0.0.1:3000/dashboards).

- **[Capstan · Session diagnostics](http://127.0.0.1:3000/d/capstan-session-diagnostics)** — основной: поиск сессий и попыток сравнения, переход на временную шкалу, связанные логи. Шаблон в репозитории Capstan: `examples/observability/capstan-dashboard.json`.
- **[Capstan · Local telemetry](http://127.0.0.1:3000/d/capstan-local)** — ранее установленный локальный дашборд. Он автоматически подключён из `telemetry-dash/capstan.json`; для новых сценариев сессий используй Session diagnostics.
- **JVM Overview**, **RED Metrics (classic histogram)**, **RED Metrics (native histogram)** — комплектные дашборды. Их наличие не означает, что Capstan отправляет необходимые им метрики. JVM-дашборд не предназначен для Capstan на C/Lua.

Основной дашборд использует **Tempo + TraceQL** для трейсов и **Loki + LogQL** для логов. Панели:

| Панель | Для чего |
| --- | --- |
| All runs | Все найденные запуски; фильтр сессии намеренно не применяется |
| Session runs | Запуски выбранной сессии |
| Benchmark runs | Поиск диагностических попыток по сравнению, задаче и повтору |
| Lifecycle logs | События жизненного цикла с фильтрами сессии и Trace ID |

Benchmark runs — не таблица результатов сравнения: время всего процесса, CPU и память остаются в отчёте запускающего инструмента. Фильтры Comparison ID / Task / Replicate ID действуют только на эту таблицу, не на логи.

## 4. Посмотреть конкретную сессию и её временную шкалу

1. [Войди в локальную Grafana](http://127.0.0.1:3000/login). Вход в браузере агента не авторизует твой браузер. В проверенном стенде без входа Explore перенаправлял на главную.
2. Открой [Session diagnostics](http://127.0.0.1:3000/d/capstan-session-diagnostics).
3. Справа сверху выбери **Last 24 hours** или нужные даты.
4. В выпадающем списке **Session name** начни вводить название и выбери результат; либо найди идентификатор в **Session ID**. Оба списка берут значения из Tempo, а выбранные значения одновременно фильтруют Session runs и Lifecycle logs.
5. В **Session runs** нажми **Trace ID**. Откроется временная шкала: дерево операций и горизонтальные полосы длительности.
6. Раскрой спан `agent.model` или `agent.tool` — там контекст и измерения операции.

Списки сессий сопоставляют значения буквально: точки и скобки экранировать не нужно. **All** снимает ограничение. При одинаковых названиях используй ID. Чтобы найти старые трейсы после переименования, выбери стабильный **Session ID**, а **Session name сбрось в All**. Иначе название ограничит результаты прежним или новым снимком имени. Trace ID и фильтры сравнений по-прежнему принимают регулярные выражения (`.*` — без ограничения).

Списки показывают только уже экспортированные значения, доступные Tempo; это не список локальных переписок. Обнови диапазон времени, если нужного значения нет. При выключенной передаче имён используй ID. Названия с обратной кавычкой исключены из списка ради безопасной подстановки в запрос — такую сессию ищи по ID. Ограничения сервера и настройки временного диапазона источника также могут сокращать список.

**Сессия** — переписка; **трейс** — путь одного запуска; **спан** — отдельная операция внутри пути. В одной сессии бывает много трейсов. `agent.run` — запуск, `agent.model` — запрос модели, `agent.tool` — инструмент. Вложенные полосы показывают дочерние операции, параллельные ветки могут перекрываться.

Название отправляется только при `observability.include_session_name = true`. Добавь этот параметр в существующий раздел `observability` конфигурации Capstan, сохранив endpoint и остальные настройки. После изменения перезапусти Capstan и выполни новый запрос. Название захватывается при начале запуска; переименование не меняет старые трейсы. У несохранённых запусков может не быть ID сессии.

**`service.name` — не все атрибуты.** Это имя приложения на уровне ресурса. ID/название сессии, модель, результат, токены и задержки ищи в раскрытом спане. Поисковая таблица отображает только часть полей.

## 5. Explore: поиск вручную

[Explore](http://127.0.0.1:3000/explore) — экран запросов к хранилищам. Сверху слева выбирается источник данных.

Выбери **Tempo**, режим **TraceQL**, диапазон времени, затем **Run query**:

```traceql
{ resource.service.name = "capstan" }
```

Для конкретной сессии:

```traceql
{ resource.service.name = "capstan" && span.session.id = "SESSION_ID" }
```

Или по имени:

```traceql
{ resource.service.name = "capstan" && span.session.name = "НАЗВАНИЕ СЕССИИ" }
```

Замени значения-заглушки своими. Нажми Trace ID найденной строки, чтобы открыть временную шкалу.

## 6. Логи и связь с трейсом

В раскрытом спане используй **Explore the logs for this in split view**. Это открывает Loki с тем же Trace ID. Из раскрытой строки лога можно перейти обратно в Tempo по ссылке trace_id.

Вручную: Explore → **Loki** → **Code** → **Run query**:

```logql
{service_name="capstan"}
```

Логи одного трейса:

```logql
{service_name="capstan"} | trace_id = "TRACE_ID"
```

Раскрой строку. Текст может быть коротким (`span.started`, `span.finished`), а полезный контекст находится в **структурированных метаданных**: операция, сессия, модель/инструмент, результат, измерения. Loki заменяет точки в именах полей подчёркиваниями: `session.id` → `session_id`.

Это диагностические события, **не полная переписка и не копия всего консольного вывода**. Промпты, ответы и команды не должны автоматически выгружаться ради диагностики.

## 7. Как понять, почему медленно

1. Найди долгий запуск и открой его трейс.
2. Посмотри самые длинные полосы запросов модели и инструментов.
3. У модели сравни длительность с `first_output_ms`: долго ждали первый содержательный вывод или долго получали остальной поток?
4. Проверь повторные попытки, ожидание разрешений, очередь и параллельных детей.
5. Открой связанные логи для результата и категории ошибки.

Не складывай вложенные и параллельные интервалы: они перекрываются. Сетевые отметки тоже могут быть накопительными. Отсутствующее измерение — не ноль. Длительность трейса — не обязательно полное время процесса, а пустой промежуток сам по себе не объясняет задержку.

## 8. Если не работает

- **Нет страницы:** проверь OrbStack, затем `docker ps -a` и запуск контейнера.
- **Есть Grafana, нет данных:** расширь время, сбрось списки сессий в **All**, остальные фильтры в `.*`, проверь включение экспорта Capstan и приёмник `http://127.0.0.1:4318`; заверши новый запрос.
- **Нет текущего корневого спана:** завершённые дети могут прийти раньше родителя; обнови после завершения запуска.
- **Нет session.name:** проверь opt-in выше. Старые данные не дополняются задним числом.
- **Нет логов по ссылке:** расширь временной диапазон, оставив Trace ID.
- **Нужно проверить сервер:** локально выполни `docker logs --tail 100 telemetry-dash-lgtm-1`. Перед передачей вывода кому-либо удали секреты и личные данные.
- **Подозрение на потерю экспорта:** сервер не покажет недошедшее событие. В Capstan есть локальный API `capstan.telemetry.diagnostics()` со счётчиками и категорией ошибки; это Lua API, не shell-команда. Эти показатели пока не отправляются в Grafana автоматически.

## 9. Перенос дашборда

В Grafana: **Dashboards → New → Import → Upload dashboard JSON file**, выбери `examples/observability/capstan-dashboard.json` из репозитория Capstan. Нужны права создания дашбордов. Выбери источники Tempo и Loki; в текущем стенде их UID — `tempo` и `loki`.

Импорт панели не разворачивает серверы и не настраивает связи источников. Для другого стенда настройки переходов Tempo ↔ Loki описаны в `examples/observability/grafana.md`. На текущем стенде они уже настроены.

## 10. Пример: сохранить OTLP в файл без Grafana

Готовая конфигурация: [otel-collector-file.yaml](otel-collector-file.yaml).
Нужен **OpenTelemetry Collector Contrib**: его [file exporter](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/main/exporter/fileexporter)
пишет стандартные данные OpenTelemetry в JSON, а не текстовый диагностический вывод.
Grafana, Tempo и Loki для этого варианта не нужны.

```text
Capstan → OTLP/HTTP → Collector Contrib → otel-output/logs.jsonl
                                      → otel-output/traces.jsonl
```

Из корня репозитория Capstan, с установленным `otelcol-contrib`:

```sh
mkdir -p otel-output
chmod 700 otel-output
otelcol-contrib validate --config examples/observability/otel-collector-file.yaml
otelcol-contrib --config examples/observability/otel-collector-file.yaml
```

Collector остаётся работать в этом терминале. Пути файлов относятся к его рабочей
директории. Используется отдельный порт **14318**, чтобы не конфликтовать с LGTM
на 4318. В существующем разделе конфигурации Capstan укажи:

```lua
observability = {
  enabled = true,
  endpoint = "http://127.0.0.1:14318",
  include_session_name = true,
}
```

Сохрани остальные нужные настройки своего раздела. Перезапусти Capstan, выполни
запрос и дождись отправки пакета. В `otel-output/logs.jsonl` будут OTLP JSON
объекты с `resourceLogs`, в `traces.jsonl` — с `resourceSpans`. Одна строка —
пакет, а не обязательно один лог или спан. Перед остановкой Collector дай
Capstan завершить экспорт; аварийное завершение не гарантирует запись всего.

Это **тот же поток событий и контекст**, только другой экспортёр на стороне
Collector. Флаг `--trace-file` не нужен. Настройка Capstan `file_exporter`
относится к его локальным журналам `capstan.log.v1`, а не к этим OTLP JSON файлам.
Здесь сохраняются структурированные события телеметрии, не вся переписка.

Пример не включает ротацию: файлы могут расти, контролируй место и права доступа.
Названия сессий могут содержать личную информацию. Для одновременной записи и
отправки в хранилище добавь файловые экспортёры в существующий Collector и
перечисли оба назначения в соответствующих `service.pipelines.*.exporters`.
Менять работающий контейнер для этого примера не требуется. Чтобы вернуться к
Grafana, восстанови endpoint `http://127.0.0.1:4318` и перезапусти Capstan.

## 11. Технологии — ссылки и назначение

- [OrbStack](https://orbstack.dev/) — запускает Linux-контейнеры на Mac.
- [Docker](https://docs.docker.com/) — среда контейнеров; [Docker Compose](https://docs.docker.com/compose/) — описание и запуск стенда из YAML.
- [Grafana otel-lgtm](https://github.com/grafana/docker-otel-lgtm) — готовый локальный комплект сервисов в одном образе.
- [OpenTelemetry](https://opentelemetry.io/docs/) — общая модель телеметрии; [OTLP](https://opentelemetry.io/docs/specs/otlp/) — протокол её передачи.
- [Collector](https://opentelemetry.io/docs/collector/) — приём и маршрутизация сигналов.
- [Grafana](https://grafana.com/docs/grafana/latest/) — веб-интерфейс и дашборды; [Explore](https://grafana.com/docs/grafana/latest/explore/) — ручной поиск.
- [Tempo](https://grafana.com/docs/tempo/latest/) — хранилище трейсов; [TraceQL](https://grafana.com/docs/tempo/latest/traceql/) — язык поиска по ним.
- [Loki](https://grafana.com/docs/loki/latest/) — хранилище логов; [LogQL](https://grafana.com/docs/loki/latest/query/) — язык запросов к логам.
- [Prometheus](https://prometheus.io/docs/introduction/overview/) — числовые временные ряды: счётчики и другие метрики. Наличие компонента в комплекте не означает наличие метрик Capstan.

Основной путь для тебя: **OrbStack → Grafana → Session diagnostics → сессия → Trace ID → временная шкала → связанные логи**.
