# Completion review на фоновых сабагентах

## Статус и исходная база

Текущая реализация фоновых сабагентов сохранена коммитом `cfb6553` (`Save background subagent implementation`). Этот документ — согласованный план, не отчёт о выполненной реализации. Имена новых внутренних API предварительные; перед изменениями сверить их с кодом. Существующие изменения сохранять, не откатывать.

## Цель

Встроенный включаемый/отключаемый плагин общего review: заявка на принятие результата → фоновый reviewer → отдельный реестр issues → автоматические исправления основным агентом → ограниченная перепроверка → итоговый ответ.

Reviewer проверяет соответствие задаче, ошибки кода, регрессии и безопасность. Не навязывает косметику, посторонний рефакторинг или создание тестовой инфраструктуры. Проверяет написанные/изменённые в рамках задачи тесты. Отсутствие тестов само по себе не issue; исключение — прямое требование задачи или действующих инструкций проекта (в Capstan такие требования есть). Посторонние тесты не аудирует. Успешная валидация не заменяет review.

## Принятые решения

- Использовать существующий `agent/subagents.lua` и общую фоновую очередь, а не новый исполнитель или ОС-процесс.
- Review запускается на готовой версии изменений, не непрерывно на каждой записи.
- Reviewer только читает; правки выполняет основной агент.
- Reviewer привязан к текущему запуску. Его отмена не затрагивает независимые фоновые группы.
- Основной агент ждёт проверку; итоговый ответ удерживается до окончания review-цикла.
- Issues существуют отдельно от tasks. `tasks.completed` означает завершение исполнителем, не независимую приёмку.
- По умолчанию максимум два цикла исправления с перепроверкой; число циклов, время и запросы конфигурируются.
- Плагин выключен по умолчанию; старые булевы значения настройки сохраняют совместимость.
- Верхний компактный индикатор виден только во время активного review-цикла.

## 1. Сверка контрактов и существующих тестов

Проверить `agent/runtime.lua`, `agent/tools.lua`, `agent/subagents.lua`, hooks/config/plugins API, профили, C bindings фоновых задач и ожидание TUI/CLI/ACP. Дочитать существующие review assertions и cancellation wrappers: предыдущие большие чтения были обрезаны.

Зафиксировать приоритет конфигурации, tracking записей/валидации, lifecycle фоновых групп, snapshots/scopes инструментов, retries, finalization callbacks, session persistence и hooks. Старую эвристику «несколько записей без успешной валидации» не сохранять как условие пропуска согласованной приёмки: тесты не заменяют reviewer. При этом не переписывать попутно эвристику распознавания shell-валидации.

Критерий: определены все затронутые пути и фактические команды узких тестов; существующие assertions меняются только при необходимом изменении поведения.

## 2. Контракт завершения и встроенный плагин

Предполагаемые файлы: `agent/completion_review.lua`, `plugins/completion_review.lua`, `agent/runtime.lua`, `agent/hooks.lua`, типы plugin/runtime API.

- Добавить единый completion gate до публикации итогового ответа.
- Добавить `request_completion`: это заявка на принятие, а не безусловное завершение.
- Обычный терминальный ответ без tool calls проходит через тот же gate, чтобы забытый tool не обходил review.
- Различать готовность, вопрос пользователю, блокировку, ошибку и отмену. Вопрос не запускает review незавершённой работы; блокировка не объявляется успехом.
- Runtime владеет defer/resume, ожиданием, отменой и exactly-once завершением; плагин — политикой проверки, заданиями и решениями принять/ожидать/продолжить.
- Не вызывать вложенный `_G.agent_entry` из `after_agent_turn`. Существующий hook остаётся уведомлением о настоящем завершении.
- Единый finalizer: ответ, `on_done`, hooks и очистка выполняются ровно один раз.
- Исключить рекурсивный review внутри сабагентов.

Критерий: явная и неявная попытки завершения используют один путь; выключенный плагин не добавляет запросов/ожидания; cancel и ошибка не оставляют зависший запуск.

## 3. Конфигурация и бюджеты

Расширить существующий `agent.completion_review`, нормализуя `false/true` в структуру. Предварительная схема:

```lua
completion_review = {
  enabled = true,
  max_fix_cycles = 2,
  max_duration_sec = 900,
  max_requests = 30,
  reviewer = { max_turns = 6 },
}
```

`900`, `30` и `6` — предложенные стартовые значения, требующие проверки на практике; два цикла согласованы как дефолт.

- `max_fix_cycles = 0`: первоначальная проверка без автоматического исправления.
- Время учитывается от заявки, включая очередь, review, исправления и проверки.
- Бюджет запросов общий для reviewer и родителя на этапе исправлений, включая retries.
- Действуют также более строгие общие ограничения запуска/scheduler; не создавать скрытые независимые лимиты.
- Проверять значения, фиксировать конфигурацию на запуск. Таймаут должен срабатывать без активного HTTP.
- Явно определить конфликт enabled review с запретом subagents; не обходить capabilities молча.
- Обновить пример конфигурации, типы и документацию.

## 4. Интеграция с фоновым scheduler

Предполагаемый внутренний API: submit/result/cancel/release с непрозрачным handle, run-bound lifetime и политикой внутренних уведомлений. Публичный инструмент subagents остаётся совместимым адаптером.

- Общая очередь, лимит параллельности, retries и tracking; без отдельной реализации scheduler.
- Доставка результата на безопасной границе polling, без вложенного ожидания HTTP.
- Идентификаторы запуска/сессии и защита от дублей и поздних callbacks.
- Отмена только собственного reviewer; независимые группы продолжают работать.
- Сохранять provider/model/profile/scopes snapshots без расширения прав.
- Учитывать, что пустой tools whitelist может означать наследование: reviewer должен получать технически ограниченный набор.
- Reviewer: depth 1, без shell, записи, tasks, вложенных subagents и произвольных MCP; без интерактивного запроса новых разрешений. Недостаток доступа означает неполную проверку.
- Hooks не должны расширять ограничения reviewer; проверять результат после hooks.

Native слой: `src/background_work.c`, `include/background_work.h`, Lua bindings. Обеспечить освобождение terminal group/task records и Lua-контекстов: registry на 128 записей нельзя постепенно исчерпывать reviews. Активные записи не удалять, ошибки публикации обрабатывать. Внутренние reviews видимы в `/processes` во время исполнения, но не дублируют обычное уведомление о завершении фоновой группы.

## 5. Workspace, барьер записи и снимки

`workdir` — база относительных путей и shell. `workspace_root` — корень проекта и стандартная граница разрешений, не список Git diff и не sandbox ОС. Сейчас оба: `/Users/alxd/narnia/capstan`.

- Зафиксировать исходное состояние до работы над задачей, включая существующие staged/unstaged/untracked изменения.
- При заявке получить стабильный permission-filtered снимок и версию: оригинальные пути, содержимое, контрольные суммы, удаления/переименования.
- Review рассматривает изменения задачи относительно baseline и необходимый контекст, а не присваивает агенту весь `git diff HEAD`.
- Не копировать/читать запрещённые файлы при построении снимка. Сохранять действующие правила доступа и исключения; `.env`, `.zshenv` и аналогичные файлы не читать.
- При отсутствии baseline/неоднозначном происхождении изменений явно сообщать ограничение, не выдумывать авторство.
- Приостановить основного агента. Кооперативный барьер workspace закрывает новые управляемые операции записи; активные потенциальные писатели должны завершиться перед снимком.
- Не считать произвольный shell/MCP безопасным; не убивать долгоживущие процессы молча. Ограничивать ожидание бюджетом и показывать причину блокировки.
- Reviewer читает неизменяемый снимок через адаптеры чтения, а не live workspace.
- Перед исправлениями и принятием проверять актуальность файлов и использованных зависимостей. Внешний drift делает результат устаревшим: остановить автоматику и спросить пользователя, не перезаписывать изменения.
- Барьер не блокирует редактор, другой Capstan или доверенный Lua с прямым I/O; контрольные суммы обнаруживают drift, но не дают атомарной защиты ОС. Эти ограничения документировать.
- Освобождать барьер и снимки на всех terminal путях.

## 6. Реестр issues и протокол verdict

Предполагаемые файлы: `agent/issues.lua`, `plugins/issues.lua`, интеграция хранения сессий.

Структурированный результат reviewer: `clean`, `findings`, `inconclusive`. Пустой, обрезанный, ошибочный или невалидный ответ не является clean.

Issue: стабильный ID, важность, описание, доказательство/нарушенное требование, файл и диапазон строк (необязательны для отсутствующей реализации), версия снимка, состояние, ответ исполнителя и результат перепроверки.

- Runtime валидирует и атомарно сохраняет отчёт reviewer; ограничивает размеры и число findings.
- Reviewer предлагает/подтверждает замечания; исполнитель отмечает «исправлено, ждёт проверки» или оспаривает с обоснованием, не удаляет замечания молча.
- Пользователь может явно принять риск.
- Привязка к запуску, ревизии и исходной версии; защита от устаревших обновлений и дублей.
- `/issues` показывает таблицу и детали независимо от tasks. Отключение плагина не удаляет историю.
- Ошибка сохранения не должна приводить к ложной успешной приёмке.

## 7. Автоматическое исправление и остановка

Состояния: draft → queued → reviewing → parent_fixes → re_review → finalized (также failed/cancelled/stale).

- Результат автоматически доставляется родителю внутренним событием, без Enter и поддельного пользовательского сообщения.
- Clean публикует удержанный ответ без дополнительного модельного запроса.
- Findings возобновляют основного агента с данными review, а не с новыми доверенными инструкциями.
- Родитель исправляет подтверждённые проблемы или обоснованно оспаривает замечания, выполняет требуемые проверки.
- Повторный reviewer проверяет открытые issues и регрессии от исправлений, не начинает новый глобальный аудит.
- Остановка по max_fix_cycles, общим бюджетам и отсутствию прогресса; оставшиеся issues явно отражаются в итоге.
- Техническая ошибка/недостаток доступа: явно неполное review, не clean. До исправлений можно сохранить исходный ответ с предупреждением; после правок нельзя вернуть устаревший черновик.
- Отмена родителя не публикует черновик как успех. Остановка только reviewer завершает проверку как незавершённую. Таймаут не обходится fallback.

## 8. TUI, CLI, ACP и наблюдаемость

- Верхний компактный фиолетовый индикатор с текстом: очередь / ревью / исправления 1/2 / перепроверка 1/2. Только активный цикл; после завершения/отмены полностью скрывается.
- Сверить верхнюю свободную область renderer. Поддержать узкий терминал, resize и монохромный fallback. Нижняя строка сохраняет текущую операцию.
- Состояние из runtime, не из текста модели и не только из наличия HTTP.
- CLI ждёт root pending, включая интервалы без HTTP, но не ждёт независимые фоновые задачи после окончательного ответа.
- TUI сохраняет очередь пользовательского ввода и корректную отмену; callback старого запуска не меняет новый.
- ACP не отправляет end_turn до приёмки/окончательной остановки, корректно обрабатывает cancel/close/disconnect и не публикует reviewer как родителя.
- Сохранять итог и issues; восстановление активного review после перезапуска не входит в первую версию.
- Телеметрия: связанный с родителем review, время очереди/выполнения, циклы/попытки, причины незавершённости; без двойного учёта и чувствительных данных.

## 10. Проверки и критерии приёмки

Расширять ближайшие существующие тесты, не заменять assertions без причины. В частности: `test_background_subagents.lua`, `test_background_runtime.lua`, `test_background_work.c`, `test_background_modes.py`, runtime/provider tests; новые focused tests политики review/issues/snapshot.

Обязательные сценарии:

1. Выключенный review не меняет завершение и число запросов; булев конфиг совместим.
2. request_completion и terminal fallback едины; вопросы/blocked/cancel не маскируются успехом.
3. Reviewer использует общий scheduler и ограниченные инструменты, включая hooks/пустой whitelist/permission denial.
4. Clean, findings, malformed/truncated/inconclusive, ошибки провайдера и сохранения.
5. Доставка ровно один раз, исправления и scoped re-review, 0/2/иной лимит циклов, no-progress и общие бюджеты с retries.
6. Cancel на очереди/HTTP/retry/исправлении; поздний результат и новая сессия; независимые группы не отменяются.
7. CLI pending без HTTP; TUI очередь ввода и индикатор; ACP не завершает ход раньше и корректно закрывается.
8. Staged/unstaged/untracked/delete/rename, исходные чужие изменения, запреты чтения, активные писатели, внешний drift и освобождение барьера.
9. Нет требований создать тесты без основания; написанные тесты проверяются; обязательные по задаче/инструкциям тесты не игнорируются.
10. Длинная серия reviews не исчерпывает native registry и не оставляет контексты/снимки; уведомления не дублируются.

Запускать узкие Lua/native проверки после соответствующих правок. По затронутым путям: `make test`, `make test-http-lua`, `make test-process-control`, `make test-tui-input`, `make test-build`. Команды сверить с текущим Makefile. Real-binary TUI/CLI/ACP проверять существующим локальным SSE-стендом, без платного API. Не повторять эквивалентные проверки без причины.

## Не входит в первую версию

Постоянное наблюдение за каждой правкой, несколько reviewers, специальная отдельная модель, произвольное расширение scope, OS sandbox/жёсткие файловые блокировки, восстановление активных reviews после перезапуска, автоматическое продолжение после уже опубликованного окончательного ответа.
